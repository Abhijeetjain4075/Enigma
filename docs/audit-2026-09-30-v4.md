## Protocol evolution

OCPI 2.3.0 covers authorisation, locations, sessions, CDRs, tariffs, tokens, commands, smart charging, hub information, invoice reconciliation, optional payments and bookings. OCPI 3.0 is in draft development.

OCPP 2.1 is IEC-standardized as IEC 63584-210:2025. Edition 2 includes certification profiles/test cases and later errata.

ISO 15118-20 received a 2026 amendment adding AC DER service, MCS service and improved security.

Sources:
- https://github.com/ocpi/ocpi
- https://evroaming.org/ocpi/
- https://openchargealliance.org/download-ocpp/

Enigma therefore needs version-aware, extension-tolerant canonical contracts.

## Data commoditization versus data quality

EU AFIR requires operator APIs and standardized public data access. Current implementing rules require static updates within 24 hours and dynamic updates within one minute after changes. A Common European Access Point is mandated for establishment by 31 December 2026.

Eco-Movement and CIRRANTIC already provide large-scale normalized/enriched charging data and reliability indicators.

Sources:
- https://eur-lex.europa.eu/eli/reg/2023/1804/2025-04-14/eng

“Aggregate charger data” is therefore not sufficient differentiation.

## Revised strategic boundary

Enigma should be a neutral orchestration/evidence layer only if experiments demonstrate a persistent problem that existing hubs, CPMSs, eMSPs, data providers and open-source infrastructure do not solve.

Priority hypotheses:
1. cross-provider transaction evidence
2. capability truth under contracts and permissions
3. failure/recovery orchestration
4. provider-neutral reconciliation
5. cross-domain transaction state
6. delegated authorization
7. reliability intelligence based on observed outcomes

These remain hypotheses, not validated product claims.

## Hard stops

Stop or pivot if existing products solve the workflow economically; no party will pay; permissions cannot be obtained; liability cannot be bounded; economics cannot cover support/dispute/reconciliation; regulation makes the model impractical; the moat depends entirely on a zero-to-one network effect; or the differentiator is merely an API wrapper.

## Required proof

Build one narrow transaction simulator and compare it against at least one real provider or hub workflow. Measure authorization, start, stop, session completeness, CDR agreement, tariff agreement, reconciliation exceptions, recovery time, onboarding time, support effort and transaction cost.

The output must be a measured residual-gap report, not a feature list.
