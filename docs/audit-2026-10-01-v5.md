# Enigma repository adversarial re-audit — 2026-10-01

## Executive verdict

This is a materially stronger repository than the earlier research-only state. The current `main` tree is a real executable simulator transaction laboratory with FastAPI, SQLAlchemy/Alembic, PostgreSQL RLS tests, deterministic provider simulators, transaction state validation, idempotency, evidence records, simulated ledger/reconciliation, Docker/Compose, CI, static analysis, dependency auditing, and operational documentation.

The repository is **not yet an enterprise production interoperability platform** and must not be described as one.

Current tree audit:

- branch: `main`
- recursive Git tree SHA: `049b8f6595345a9400413a0d3608a880e2c1a5e9`
- total tree entries: 109
- files: 99
- directories: 10
- CI workflow present
- prompt/manus present
- real provider adapters: absent
- real payment/settlement rails: absent
- production deployment evidence: absent

The repository's own implementation-status document correctly maintains a no-go boundary for production transaction processing.

## Audit methodology

This pass used five independent lenses:

1. **Repository integrity** — recursive tree, executable source, migrations, tests, CI, container files, prompt and status records.
2. **Runtime architecture review** — state machine, persistence, idempotency, tenancy, authentication, evidence, ledger/reconciliation, failure handling and API boundaries.
3. **Security review** — authentication, authorization, rate limiting, request limits, secrets, supply chain, container hardening, tenant isolation and external-input trust.
4. **Reliability review** — retries, concurrency, event ordering, duplicate delivery, durable delivery, reconciliation and recovery.
5. **External falsification** — current interoperability/roaming evidence and current security/supply-chain guidance.

This is a repository/static audit plus current-source review. It is not a penetration test, formal verification, provider certification, accounting audit, legal opinion, or production capacity certification.

# 2. Highest-priority findings

## P0 — Real-provider control plane does not exist

The repository intentionally contains no real provider adapter.

This is correct for the simulator-first stage, but it is the largest boundary between the current software and the intended Enigma product.

Missing:

- real provider credentials
- provider contract model
- provider authorization scopes
- provider webhook ingestion
- provider protocol adapters
- provider retry semantics
- provider-specific capability negotiation
- provider-specific error mapping
- provider support/escalation
- real session lifecycle
- real CDR ingestion
- real tariff ingestion
- real payment integration
- real refund integration
- real settlement
- real dispute flow
- production evidence

**Required next proof:** one authorized sandbox or provider, one narrow workflow, repeated transactions, evidence capture, failure recovery and reconciliation.

Do not integrate dozens of providers before one integration is proven.

---

## P0 — Production identity/authorization model is incomplete

The current application-key model effectively maps an API key to a tenant.

There is no implemented:

- user identity layer
- OAuth/OIDC
- service-account lifecycle
- RBAC
- ABAC
- permission scopes
- resource-level policy model
- administrative roles
- provider-specific authorization delegation
- credential rotation workflow
- key revocation lifecycle
- key expiry
- key ownership metadata
- last-used metadata
- audit of credential administration

This is explicitly acknowledged by the implementation-status document.

The current tenant boundary is useful for the laboratory but is not sufficient for enterprise authorization.

OWASP explicitly identifies broken object-level authorization, broken authentication and broken function-level authorization as major API security risks. citeturn1search3

### Required design

Introduce separate concepts:

`principal -> credential -> tenant -> role/scope -> resource -> operation -> policy decision`

Do not collapse identity, authentication and authorization into one API-key lookup.

---

## P0 — No durable distributed event/outbox architecture

The application records transaction events in the database, but there is no production-grade:

- transactional outbox
- message broker
- durable delivery queue
- consumer offset
- dead-letter queue
- retry schedule
- event publication acknowledgement
- replay service
- event schema registry
- cross-service delivery contract

This becomes critical once real providers are connected.

The database event record and an external event publication must be made atomic from the business perspective.

### Required pattern

Transaction:

`business state + event + outbox record`

committed atomically.

Then:

`outbox -> publisher -> broker -> consumer -> acknowledgement`

with deterministic retry/replay behavior.

Do not claim exactly-once delivery. Design for at-least-once delivery plus idempotent consumers.

---

## P0 — Idempotency is not yet concurrency-safe enough for production

The repository has a strong conceptual idempotency design:

- tenant/key uniqueness
- request hashing
- response replay
- conflict on changed payload

However, the normal pattern is still:

`read existing key -> perform work -> insert idempotency record`

Concurrent identical requests can race before the unique constraint is inserted.

Production implementation needs an atomic database strategy.

Required behavior:

- same key + same request -> one canonical operation/result
- same key + different request -> deterministic conflict
- concurrent requests -> no duplicate side effects
- failed transaction -> clearly defined retry semantics
- in-progress operation -> explicit state
- provider call uncertainty -> reconciliation rather than blind replay

For physical-world and financial operations, this is critical.

---

## P0 — Webhook trust boundary is absent

The current laboratory does not ingest real webhooks.

Production Enigma will need:

- signature verification
- timestamp validation
- replay protection
- provider credential rotation
- source allowlisting where appropriate
- payload schema validation
- provider-specific authenticity rules
- event deduplication
- event ordering handling
- quarantine for invalid messages
- dead-letter handling
- evidence retention

RFC 9421 HTTP Message Signatures and mTLS/OAuth mechanisms are relevant building blocks, but provider-specific contracts must determine the final implementation.

Never trust a provider webhook merely because it arrives over HTTPS.

---

This is correct.

However, the current ledger is not yet sufficient for a real financial platform.

Missing:

- immutable accounting period

- journal/batch identity
- debit/credit semantic constraints
- posting date vs event date
- tax treatment
- fee treatment
- payable/receivable lifecycle
- settlement batches
- bank/payment-provider references
- FX conversion records
- rounding rules
- invoice linkage
- credit/debit notes
- chargebacks
- dispute states
- accounting export
- period close
- correction/reversal controls

The current zero-sum simulation proves only a laboratory invariant.

It does not establish financial correctness.

## P0 — Reconciliation model is transaction-centric rather than settlement-grade

The current `ReconciliationRecord` is intentionally small and useful for the simulator.

Production reconciliation must support at least:

- transaction-level
- session-level
- CDR-level
- invoice-level
- payment-level
- refund-level
- settlement-level
- provider statement-level
- accounting-period-level reconciliation

It also needs:

- matching strategies
- confidence

- manual resolution
- evidence links
- resolution history
- ownership
- SLA
- escalation
- immutable reconciliation decisions

A single reconciliation record per transaction will not scale to the intended financial topology.

# 3. P1 security findings

## P1 — CI dependencies are tag-pinned rather than immutable SHA-pinned

The workflow uses actions such as:

`actions/checkout@v7`

and:

`actions/setup-python@v7`

GitHub's current security guidance states that pinning actions to full-length commit SHAs is the immutable option and specifically recommends it for supply-chain protection. citeturn1search0

### Required

Pin third-party actions to verified full commit SHAs.

Maintain a documented update process.

Do not blindly update SHAs.

---

## P1 — Container base images are tag-pinned rather than digest-pinned

The Dockerfile uses:

`python:3.12-slim`

and Compose uses:

`postgres:16-alpine`

Tags are mutable.

Docker's current guidance recommends digest pinning when reproducibility and supply-chain integrity matter. citeturn1search1turn1search2

### Required

Pin production-critical images by digest.

Use Dependabot/Renovate or an equivalent controlled update process.

Record image provenance.

---

## P1 — Runtime API keys are environment configuration, not an enterprise credential subsystem

The current configuration is appropriate for a laboratory.

Production requires:

- hashed credential storage where feasible
- key identifiers
- secret material separation
- rotation
- revocation
- expiration
- scope
- tenant ownership
- audit history
- emergency disable
- administrative approval
- break-glass process

Never put long-lived production API secrets into ordinary application configuration without a dedicated secret-management architecture.

---

## P1 — Request-size enforcement is incomplete against streaming/chunked bodies

The current middleware checks `Content-Length`.

A client can omit Content-Length and use chunked transfer encoding.

A production API gateway and/or ASGI receive-layer control must enforce an actual byte budget, not only a declared length.

OWASP identifies unrestricted resource consumption as a major API risk and recommends server-side limits for payload size and resource usage. citeturn1search6

---

## P1 — Rate limiting is intentionally process-local

The current limiter is explicitly documented as a local guardrail.

That is correct for the lab.

It is not sufficient for:

- multiple API instances
- autoscaling
- distributed attacks
- per-tenant quotas
- per-key quotas
- per-operation quotas
- financial operation throttles
- provider-specific budgets

Production needs gateway/distributed enforcement.

---

## P1 — No formal security verification of authorization matrix

Current tests strongly validate tenant isolation.

They do not yet validate a future enterprise authorization matrix because RBAC/ABAC/scopes are not implemented.

Before production, build an authorization test matrix covering:

- tenant
- organization
- user
- service account
- provider
- transaction
- credential
- operation
- role
- scope
- delegation
- time
- geography
- spend limit
- service type

## P1 — Provider uncertainty needs explicit state

A particularly important production state is:

**unknown whether external side effect happened.**

Example:

1. Enigma sends start.
2. Network timeout occurs.
3. Provider may have started the session.
4. Enigma cannot safely retry blindly.

The state must become something like:

`external_outcome_unknown`

and trigger reconciliation.

This should be a first-class domain concept rather than simply `failed`.

---

## P1 — Physical-world commands need stronger safety semantics

The current simulator correctly labels actions as simulated.

- operation risk class

- timeout policy
- uncertainty policy
- compensation policy
- operator escalation
- maximum retry count
- emergency stop behavior where relevant

Do not treat:

`start charging`

as equivalent to:

`GET /resource`.

# 11. New domain concept required: uncertainty

The current state machine needs a formal uncertainty layer.

Recommended distinction:

### Business state

What Enigma believes the transaction state is.

### Provider state

What the external provider reports.

### Observed state

What Enigma directly observed.

### Evidence state

What evidence supports each claim.

### Outcome certainty

One of:

- confirmed
- probable
- uncertain
- contradicted
- unknown

This distinction is potentially more important than adding more transaction statuses.

---

# 12. New domain concept required: capability authority

A provider may expose a capability technically but Enigma may not have contractual permission to invoke it.

Therefore capability should be modeled as:

`technical capability × commercial entitlement × credential permission × tenant permission × resource state`

Only the intersection should produce an executable capability.

This should become a first-class authorization/capability decision object.

---

# 13. New domain concept required: evidence graph

The current evidence table is a good foundation but a production evidence model should support relationships such as:

`claim -> evidence -> observation -> provider response -> transaction -> event -> reconciliation -> resolution`

This permits later reconstruction of:

**what happened, according to whom, when, and why Enigma believed it.**

That is a potentially meaningful Enigma differentiator.

# 20. AI/automation boundary

Do not put an LLM directly in the authoritative transaction state machine.

AI can assist with:

- incident diagnosis
- anomaly explanation
- provider documentation analysis
- mapping suggestions
- reconciliation triage
- operator assistance
- natural-language queries
- research

AI should not autonomously decide:

- whether money moved
- whether a physical charging command succeeded
- whether a refund is owed
- whether evidence is authentic
- whether a transaction is legally settled
- whether a security control can be bypassed

Authoritative state transitions must remain deterministic and policy-controlled.

---

# 21. Architecture decision that should remain fixed

The repository should retain:

**simulator first -> narrow real provider -> repeated evidence -> controlled production**

Do not reverse this order.

The next engineering objective should not be another large documentation expansion.

It should be a deterministic proof that Enigma adds measurable value beyond a conventional roaming/provider composition.

# 23. Final audit conclusion

### Current status

**Research + executable transaction laboratory.**

### Production status

**Not production-ready.**

### Strongest current assets

- unusually explicit research/evidence discipline
- simulator-first strategy
- deterministic state machine
- tenant isolation
- PostgreSQL RLS testing
- append-only event protection
- idempotency foundation
- evidence/provenance foundation
- reconciliation foundation
- failure injection
- fail-closed simulator boundary
- CI/security/migration discipline

### Most important weaknesses

1. no real provider
2. no enterprise identity/authorization
3. no durable event/outbox system
4. no production webhook trust boundary
5. no financial-grade ledger/settlement model
6. no distributed reliability infrastructure
7. no production observability stack
8. no real operational/SLO ownership
9. supply-chain pinning is incomplete
10. strategic differentiation remains experimentally unproven

### Strategic verdict

The repository is now sufficiently mature to stop expanding documentation indiscriminately.

The highest-value next step is **proof**.

The decisive experiment is:

**real provider/sandbox -> real authorization -> real session -> real CDR -> evidence -> reconciliation -> injected/observed failure -> recovery -> repeated measurement**

If Enigma cannot demonstrate a measurable residual advantage over existing roaming/CPMS/eMSP/provider compositions, the architecture should pivot rather than accumulate features.

If it can, the evidence should become the foundation for the next production architecture.
